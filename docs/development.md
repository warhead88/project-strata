# Правила разработки

## Код

- Форматирование задаёт `rustfmt`. Имена типов и функций берём из предметной области. Если величину можно перепутать с другой, выражаем различие в типе или указываем единицу в имени. Публичный API описывает доступные операции, единицы измерения и условия ошибки. Внутренние типы и поля по умолчанию закрыты.
- У каждого изменяемого состояния есть владелец. Например, клиент передаёт команду на изменение бюджета, а её допустимость проверяет крейт, отвечающий за бюджет. Ту же операцию вызывает ИИ. Это даёт одну точку для изменения правила и его проверки без окна и GPU.
- Пишем на безопасном Rust. Корневой `unsafe_code = "forbid"` действует во всех наших крейтах, включая тесты. При работе с графикой и нативными библиотеками используем безопасные API зависимостей. Внутри сторонней зависимости может быть `unsafe`.
- Ожидаемые ошибки ввода, загрузки контента и выполнения команд возвращаем через `Result`. Допустимое отсутствие значения выражаем через `Option`. При передаче ошибки добавляем контекст, по которому можно найти причину, например путь к файлу и идентификатор записи.
- Оптимизацию обосновываем замером на воспроизводимой нагрузке. Указываем масштаб мира, скорость игрового времени, профиль сборки и оборудование. Для рендера сравниваем время кадра, для симуляции — длительность шага и отставание от заданного темпа.

## Кто пишет тесты и что проверяет

За проверку отвечает автор изменения в том же треде. В начале задачи он формулирует наблюдаемый результат и находит ближайший тест. Если существующая проверка уже покрывает результат, достаточно запустить её. Недостающий тест автор пишет вместе с реализацией и включает в тот же коммит. Отдельный тред уместен для самостоятельной задачи, например разработки нагрузочного стенда.

| Что меняется | Что проверяем |
|---|---|
| Правило мира или решение ИИ | Через API владельца задаём исходное состояние и команду. Проверяем результат и существенную для правила границу. Например, для перевода средств сумма списания равна сумме зачисления, а при отклонённом переводе оба баланса сохраняются. Тест работает без окна и GPU. |
| Взаимодействие подсистем | Интеграционный тест на стороне потребителя проверяет передачу результата через настоящий публичный API. Для контракта детерминизма сравниваем состояние на одном тике при одинаковых исходных данных, seed и командах. |
| Контент и сохранения | Загружаем небольшой пример, проверяем ссылки и диагностику ошибочной записи. При смене формата используем также образец предыдущей поддерживаемой версии. |
| Дефект | Воспроизводим случай, на котором до исправления тест падает, а после проходит. Для визуального дефекта, который можно оценить только в клиенте, записываем в PR шаги воспроизведения и результат повторной проверки. |
| Клиент и документация | Преобразование ввода в команду можно проверить автоматически. Видимый результат проверяем в клиенте. Для правки текста проверяем точность утверждений, ссылки и затронутые команды. |

## Проверки

Версии инструментов задаёт `rust-toolchain.toml`, версии разрешённых зависимостей хранит `Cargo.lock`. Обновления включаем в коммит, цель которого объясняет смену версии. Полный перечень линтов живёт в корневом `Cargo.toml`.

Предупреждения rustc считаются ошибками. Для Clippy включены группы `all` и `pedantic`. Отдельные линты запрещают `unwrap`, `expect`, явный `panic!`, отладочный `dbg!` и заглушки `todo!` и `unimplemented!`. В release включена проверка целочисленного переполнения. Если правило игры предусматривает насыщение, циклическую арифметику или обработку выхода за диапазон, выбираем соответствующую операцию явно.

Для обоснованного исключения из линта применяем `#[expect(..., reason = "...")]` у конкретного выражения или элемента. В причине указываем проверяемое условие, благодаря которому код корректен. Устаревшее ожидание даст предупреждение. Запрет `unsafe` исключений не допускает.

Во время работы запускаем ближайший тест или проверку крейта. Перед завершением запускаем из корня `cargo verify`. Эта команда проверяет лимиты файлов, форматирование, Clippy для всех целей и включаемых возможностей, тесты и сборку workspace с зафиксированными зависимостями. Проверку графического поведения при изменении клиента описываем отдельно в PR.

## Git и GitHub

- `main` в приватном репозитории GitHub — общая точка интеграции. Для задачи создаём короткоживущую ветку от актуальной `main`. Одновременно работающим тредам выделяем отдельные ветки и рабочие каталоги через `git worktree`. Зависимость от ещё не влитой ветки указываем явно.
- Один коммит — одно законченное изменение, которое можно проверить и при необходимости отменить целиком. Исправление, его регрессионный тест и связанное изменение контракта входят в один коммит, даже если затронуты несколько крейтов. Самостоятельный рефакторинг и изменение игрового правила получают отдельные коммиты, если каждый шаг сохраняет рабочую сборку. Заголовок кратко называет результат, например `Reject duplicate settlement IDs`.
- Как только изменение проверено, включаем все относящиеся к нему файлы в коммит и сразу отправляем его в рабочую ветку на GitHub. При первой отправке задаём upstream через `git push -u origin HEAD`, затем достаточно `git push`. Перед следующей задачей или передачей треда проверяем `git status -sb` и совпадение SHA локального HEAD и удалённой рабочей ветки. Если отправка сорвалась, восстанавливаем публикацию или сообщаем о препятствии и локальном SHA.
- Один pull request решает одну задачу и может содержать несколько таких коммитов. Issue заводим для работы, которую нужно запланировать, обсудить или передать другому треду. В описании PR указываем изменение поведения, способ проверки и ссылку на принятое решение, если оно затронуто. Принятое решение хранится в `docs/`, чтобы его можно было прочитать вместе с соответствующей версией кода.
- Перед слиянием просматриваем diff и результат `cargo verify` в GitHub Actions. При работе в одиночку автор сам проводит этот просмотр. Временные коммиты сворачиваем в рабочей ветке, самостоятельные сохраняем. Опубликованную историю `main` не переписываем. При необходимости возвращаем предыдущее поведение отдельным `git revert`.
